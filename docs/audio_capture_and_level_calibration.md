# 音频采集、播放音量与响度标定

更新：2026-09-07。状态：核查与后续采集设计，尚未实现实时采集或在本机做音量矩阵实验。本轮没有调整用户音量、合成增益或重新生成数据。

## 已确认的项目现状

用户反馈自身脚步可能偏响。`causal_render.py` 的素材库将脚步调向RMS 0.065，同时受峰值0.55限制；全局混音增益0.6。自身脚步直接保留双声道，不走外部脚步的距离衰减。这些是试听参考电平，没有恢复游戏自身脚步总线的实际增益。客户端原声不等于游戏最终输出电平，自身脚步的相对大小仍需实录校准。

当前模型处理文件数据，项目尚未接入WASAPI实时采集。不能把“支持一种捕获方式”表述为本机已经证明音量不变。

## 官方资料与适用边界

Windows支持捕获渲染端的数字音频流；普通系统loopback捕获端点混音，其实现可能使用硬件loopback或音频引擎复制。见 [Microsoft：Loopback Recording](https://learn.microsoft.com/en-us/windows/win32/coreaudio/loopback-recording)。

Microsoft提供按进程及其子进程捕获的示例，可排除其他应用，且不绑定单一物理输出端点；该示例要求Windows build 20348及以上。见 [Application loopback audio capture](https://learn.microsoft.com/en-us/samples/microsoft/windows-classic-samples/applicationloopbackaudio-sample/)。进程筛选本身不等于所有音量控制都被绕过。

Microsoft的AEC/APO文档明确区分音量前与音量后的参考loopback流，音量前采集可避免对应下游音量影响。这个条目属于AEC参考流说明，不能据此对每种普通应用采集、驱动或混音器控制作统一保证。见 [Reference Loopback Stream](https://learn.microsoft.com/en-us/windows-hardware/drivers/audio/windows-11-apis-for-audio-processing-objects#reference-loopback-stream)。Windows端点主音量与应用会话音量是不同控制，见 [Volume Controls](https://learn.microsoft.com/en-us/windows/win32/coreaudio/volume-controls)。

补充核查找到更直接的用户态API依据：[AUDCLNT_STREAMOPTIONS](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/ne-audioclient-audclnt_streamoptions) 明确说明默认loopback在音量/静音之前取流，`POST_VOLUME_LOOPBACK`才请求在之后取流。[KSPROPERTY_AUDIOLOOPBACK](https://learn.microsoft.com/en-us/windows-hardware/drivers/audio/ksproperty-audioloopback) 将该控制具体界定为端点音量/静音，并介绍Windows 11 24H2的驱动能力查询。故隔离系统播放端主音量有接口依据；它不等于绕过游戏内部或会话已经施加的增益，也不保证位于全部DSP之前。本机读到OS版本10.0.26200.0，尚未验证具体音频设备行为。

| 调节位置 | 对数字采集与距离判断的影响 |
|---|---|
| 采集点之后的耳放/耳机模拟音量 | 不改变上游数字采样；部分USB耳机旋钮实际控制Windows音量，须区别 |
| Windows扬声器/耳机主音量 | 在该控制之前采集可解耦；选定API、设备和驱动后实测确认 |
| Windows音量混合器中的PUBG单应用音量/静音 | 属于会话控制，单独验证，不能从主音量不影响推断这一项也不影响 |
| 游戏内部主音量、音效音量、瞬时音量降低功能 | 若游戏已在PCM中应用增益，系统侧捕获会保留该变化；应固定/记录游戏设置 |
| 声音增强、均衡、动态压缩、空间化 | 取决于处理与采集的先后；不仅改变响度，还可能改变距离和方位线索 |

## 距离歧义与拟采用策略

录到的幅度同时受声源基础强度、距离衰减和采集点之前的增益影响。较近的低音量声与较远的高音量声可能有相同幅度。左右声道同乘增益一般保持声道比例及时间差，但绝对距离无法仅凭响度唯一确定。

后续优先验证按PUBG进程采集，并把“只调个人收听音量时原始采样电平稳定”作为验收条件。游戏内部设置保持可记录的参考值，先校准自身/外部脚步、车辆和枪声之间的比例，再校准每类距离曲线。距离仍以粗远近为目标，结合声类、频谱、时序等经实录验证的线索。

F028将此明确为采集验收要求：相同游戏输出下，Windows主音量/耳机收听音量变化不能让模型距离随之改变。优先从已验证的音量前数字路径取流、固定双声道格式、统一重采样和特征处理；以同源录音对齐后比较PCM、电平、频谱、声道关系及模型输出。未完成这一步前，不宣称已经实现跨设备/音量一致性。

不能逐段归一到同一响度后声称保留了绝对距离信息。整体增益增强可以训练鲁棒性，但不能消除增益与距离的不可辨识性；后续应单独评估其对距离输出的影响，必要时降低距离置信或使用经过验证的增益补偿。补偿应使用实际线性增益/dB，不能直接拿Windows界面的百分数当作线性振幅；静音、裁剪及动态压缩不能靠相除完整恢复。

## 声卡差异与采集分支

目标数据流为：游戏固定设置输出 → 可验证的数字采集 → 模型；个人监听分支再经过收听音量、设备音效、DAC和耳机。这个顺序是拟采用设计，不是对当前所有loopback路径的描述。

- 若在DAC和模拟放大之前取得数字流，声卡的模拟底噪、失真、驱动力和耳机音质不会回写到该数字流；这些影响人听到的声音。
- 驱动/APO或硬件DSP可以在数字阶段改变频谱、响度和声道；更换设备也可能改变格式、声道数、重采样及游戏输出配置。微软说明SFX/MFX/EFX位于不同处理位置，其中端点效果即使RAW也可能保留，因此不能把“RAW”当成完全无音效的保证。见 [APO Architecture](https://learn.microsoft.com/en-us/windows-hardware/drivers/audio/audio-processing-object-architecture)。
- 对送入模型的分支，应排除或固定响度均衡、自动增益、EQ、设备虚拟环绕等处理，并保持游戏自身HRTF配置与训练一致；在不同输出设备上做相同源的对照。
- 若直接采集仍受设备处理影响，备选为固定的虚拟音频端点：游戏输出到固定格式/固定增益端点，数字流供模型，另一路监听到用户声卡，监听音量位于分流之后。该方案需要额外音频路由和延迟评估，尚未安装驱动或更改默认设备；游戏内部与分流之前的会话音量仍须固定或校准。

任意修改游戏内音量仍要求可知的、经过标定的增益关系；未知混音、静音、限幅或压缩后的信号不能保证恢复。采集分流解决下游收听音量影响，不能消除已写入游戏波形的改变。
